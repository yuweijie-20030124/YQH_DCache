# Compact CHI Credit 与 Retry 复习卡

更新：2026-10-18。范围：本地 Compact CHI 草稿的 DCache–L2 参考设计；不是完整 AMBA CHI 的 P-Credit。

一句话：Credit 是对接收方容量的约定；本地有空位不代表远端也有空位，消息在路上时也必须保留其接收容量。

## 规则对照

| 场景 | Credit 谁给谁 | 本例用途 |
|---|---|---|
| 普通请求首次发送 | L2 给 L1 动态额度 | L2 内部约定的资源 |
| 普通请求被资源 Retry 后重发 | L2 给 L1 所需静态额度 | 为重试请求准备的资源 |
| 静态流控的 Snoop 入口 | L1 给 L2 静态额度 | L1 消息接收 Buffer/ProbeQueue 容量 |

上述 TXREQ 动态、RXSNP 静态组合是手册的参考设计。具体端口选择与资源映射由实现约定。

## 资源 Retry

```text
足够动态 Credit -> 首次发请求，AllowRetry=1
收到 PRETRY 通知 -> 保留请求上下文
等齐通知要求的静态资源额度
重发原逻辑请求，AllowRetry=0
之后正常返回数据/完成响应
```

- PRETRYTXNID 标识被重试的原始请求。
- PRETRYCRD 指出需重新获得的资源类别，类别编号不是协议固定的某种硬件。
- 静态资源在消费前不能被收回或改配给其他 Requester。
- 收到 Retry 不等于 Load 完成；在当前示例中保留原 MSHR。
- 动态收回请求若被拒绝，并不会增加可用 Credit。

## Snoop 容量示例

L1 有两个队列位置，已给 L2 两个额度。L2 用一个额度发出 SNP，即使这条 SNP 还没到 L1，它也占有一个接收容量承诺。另一额度尚未使用，也已经承诺给 L2。不能因为队列暂时还是空的，就又发两个额度。

在这个单发送方、一个 Credit 对应一个队列位置的例子里，要把以下容量一起核算：

```text
队列已占位置 + 在途消息所需位置 + 已授予但尚未使用额度对应的位置
```

三者不能超过队列容量。此式是该示例的逻辑容量核算，不是规范固定的寄存器实现或跨端同周期计算规则。若授予信号本身也有传输延迟，发送新授予时就必须把承诺记账。

## 实现检查

- 明确每种 Credit 的接收方和对应资源，不能把方向反了。
- 避免对同一空位重复授予额度。
- 不得仅因接收队列当前为空就忽略已发额度和在途消息。
- 释放队列位置与协议事务结束可以是不同事件；后续处理必须仍有容量承接。
- 单周期 Retry/授予通知必须正确接收和记账。

## 五道自测

1. L1 有空闲 MSHR，但缺所需 L2 动态 Credit，能否首次发请求？
2. Credit 已用于请求且数量为零，收到收回要求应接受还是拒绝？
3. Retry 要求两种资源，只准备好其中一种，能否重发？
4. 静态流控的 L2->L1 SNP，应由谁提供接收 Credit？
5. 接收队列为空，但已授出的额度还在发送方手里，能否把同一容量再授予一次？

<details>
<summary>答案</summary>

1. 不能。本地资源不能替代下游额度。
2. 拒绝，不能返还已经消耗的额度。
3. 不能，等待所有被要求的资源满足。
4. L1，作为 SNP 的接收处理方向 L2 授予额度。
5. 不能，否则重复承诺相同容量，消息到达时可能溢出。

## 补充：三个不同条件

| 事物 | 表示什么 | 不表示什么 |
|---|---|---|
| L1 已有 MSHR | 本地能够保存未完成请求 | L2 已有处理资源 |
| Retry 所需静态 Credit 已到 | 重发所需下游资源额度已具备 | 读取的数据已经返回 |
| 对应 CompData 已到 | 收到这笔读请求的数据和响应状态 | 所有本地回填、确认、消费者义务自动全部结束 |

在本例动态加 Retry 的端口中，首次发送消耗动态额度；被 Retry 后，要等规定的静态额度才能重发。静态 Credit 消费前不能被收回或改配，但它也可用于静态流控端口，不只用于 Retry。
